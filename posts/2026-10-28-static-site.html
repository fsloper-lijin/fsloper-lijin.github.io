把博客搬回纯静态：一次极简主义的实践

2026 年 10 月 28 日 · 约 7 分钟 · 技术 GitHub Pages

过去五年我换过四套博客系统：WordPress、Hexo、Gatsby、Next.js。 每一套都能用，每一套都在两年内让我失去了继续维护的欲望。

最后一次清理的时候，我统计了一下旧项目的依赖数量：1247 个 npm 包。 为了渲染几篇 Markdown 文章，我引入了一千多个我从未读过的模块。 这不是工程，这是负债。

取舍：我要放弃什么

在决定重写之前，我先列了一张表，明确哪些功能是真正需要的：

需求是否保留理由
Markdown 写作放弃直接写 HTML，一年二十篇，够用
评论系统放弃邮箱就够了，而且更安静
标签分类保留纯静态标签，手写即可
深色模式保留三十行 CSS 变量
全文搜索放弃文章不到五十篇，目录页就够
RSS保留一个 XML 文件，用户真的在用

这张表最有价值的部分不是"保留了什么"，而是"放弃的理由都很朴素"。 大部分博客功能的存在，是为了解决作者想象出来的需求，而不是读者真实的需求。

结构：一个约定胜过十份配置

最终的文件结构是这样的：

blog/
├── index.html          # 首页
├── about.html          # 关于
├── posts/
│   ├── 2026-11-10-hello.html
│   └── 2026-10-28-static-site.html
├── assets/
│   ├── css/style.css   # 全部样式，单文件
│   └── js/main.js      # 全部脚本，单文件
├── .nojekyll           # 告诉 GitHub Pages 不要走 Jekyll
└── README.md

命名约定是核心：posts/YYYY-MM-DD-slug.html。 看到文件名就知道发布时间和主题，排序时按文件名排就是按时间排。 不需要 front matter，不需要构建脚本，不需要元数据库。

关键实现细节

1. 防止深色模式闪烁

这是纯静态站点最容易被忽略的细节。如果主题在 DOMContentLoaded 之后才应用， 用户会看到一瞬间的白屏。解法是把判断逻辑内联到 <head> 里， 在 CSS 绘制之前就把属性写好： 

<script>
(function () {
  try {
    var t = localStorage.getItem('blog-theme');
    if (!t) {
      t = window.matchMedia && window.matchMedia('(prefers-color-scheme: dark)').matches
        ? 'dark' : 'light';
    }
    document.documentElement.setAttribute('data-theme', t);
  } catch (e) {}
})();
</script>

这段代码必须同步执行、且不能放在 defer 脚本里。同时用 try/catch 包住，因为 Safari 隐私模式下访问 localStorage 会直接抛异常。

2. 用 CSS 变量做主题

只需要定义两套变量，其余所有样式都引用变量。切换主题就是改一个属性值： 

:root {
  --bg: #fbfaf8;
  --text: #17161a;
  --accent: #b8451f;
}

html[data-theme="dark"] {
  --bg: #101114;
  --text: #e9e7e3;
  --accent: #f0805a;
}

body {
  background: var(--bg);
  color: var(--text);
  transition: background-color .35s ease, color .35s ease;
}

这里有个小技巧：给 background-color 加过渡，切换主题时会有柔和的渐变， 而不是生硬地闪一下。成本是一行 CSS，收益是质感。

3. 滚动进入动画

用 IntersectionObserver，十行代码，性能远好于监听 scroll 事件： 

const io = new IntersectionObserver((entries) => {
  entries.forEach((e) => {
    if (e.isIntersecting) {
      e.target.classList.add('is-visible');
      io.unobserve(e.target);   // 只触发一次
    }
  });
}, { threshold: 0.12 });

document.querySelectorAll('.reveal').forEach((el) => io.observe(el));

注意 io.unobserve() 那行——动画只播一次。反复触发是滚动动画最常见的廉价感来源。

部署：推上去就完事

GitHub Pages 的配置成本接近于零：

  1. 新建仓库，命名 username.github.io（这样是根域名）或任意名字（走子路径）；
  2. 把文件推送到 main 分支；
  3. 仓库 Settings → Pages → Source 选 main / root，保存。

一分钟后访问 https://username.github.io。

有个坑值得提前说：如果你的仓库名不是 username.github.io， 站点会挂在 /repo-name/ 子路径下。这时所有绝对路径都会失效。 所以全站必须用相对路径（../assets/css/style.css 而不是 /assets/css/style.css）， 这是这套方案里唯一需要自律的地方。

值不值得

坦白说，如果你一年只写三篇文章，纯静态的收益不明显，用现成平台更省事。 但如果你打算长期写——写到五年、十年——那么拥有一个不会被平台修改的发布渠道本身， 就是最大的价值。

维护成本确实存在，只是它从"升级依赖、修复构建报错"变成了"手动改一行 HTML"。 前者消耗的是注意力和耐心，后者消耗的是三十秒。我选后者。
